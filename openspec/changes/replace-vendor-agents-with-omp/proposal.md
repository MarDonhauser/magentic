## Why

Magentic integrates coding agents one vendor at a time, and the integrations are not equal. `AgentProvider` (`core/provider.go`) carries four implementations — Claude Code, Codex, Copilot and Antigravity, with Gemini retired into an alias — but only `claudeProvider` returns a conversation normalizer; the other three answer `(nil, false)`, so three of the four launchable vendors have no Conversation at all. Only Claude declares `RuntimeManaged`, so only Claude can run headless; the other three are still driven by typing into a terminal. Five agent kinds ship detection manifests, and recorded pane fixtures exist for two of them. `hookinstall.go` writes hooks into `~/.claude/settings.json` and nowhere else. `workhistory_adapters.go` is 1056 lines of five separate readers for five on-disk history formats, and the pricing table in `core/stats.go` knows Claude's prices only.

The pattern is the problem rather than any one gap. Every capability Magentic adds has to be re-earned per vendor, the vendor that gets it first is always Claude Code, and the cost of adding the fifth vendor is the cost of the first. PRODUCT.md principle 4 commits to agent-agnostic orchestration, and the implementation has been drifting away from that commitment with each feature.

`omp` (oh-my-pi) has already paid this cost. One binary fronts sixty-plus model providers behind one protocol, and it exposes that protocol to a host: `omp --mode rpc-ui` speaks NDJSON over stdio with a documented command vocabulary and a lifecycle event stream. Verified against the build installed on this machine (`omp/18.2.8`): the handshake announces `{"type":"ready","protocolVersion":1,"supportedProtocolVersions":[1,2],"maxFrameBytes":1048576}`, and `get_state` answers with `sessionId`, `model` (id, provider, api, baseUrl), `thinkingLevel`, `fastModeActive`, `contextUsage`, `isStreaming`, `steeringMode`, `interruptMode` and `queuedMessageCount`. Those are exactly the facts Magentic scrapes off a pane today, offered as data.

This change stops integrating vendors and integrates one protocol. Under it, omp is the agent and the model provider is a setting.

## What Changes

- **omp becomes the runtime for every coding-agent Session.** `AgentRuntime` gains `omp`, and `omp` becomes the only runtime a new coding-agent Session is given. tmux keeps terminal Sessions and the terminal dock; it stops hosting coding agents. **BREAKING**: a coding-agent Session no longer has a pane to `attach` to, and the vendor picker stops choosing a binary.
- **Model, thinking level and fast mode become Magentic's own controls.** The session-control surface reads `get_state` and writes `set_model`, `cycle_model`, `set_thinking_level`, `cycle_thinking_level`, `set_fast_mode`, `compact` and the steering, follow-up and interrupt modes. Context usage becomes an observed fact rather than a number parsed out of a status line.
- **The model replaces the vendor as what the interfaces show.** Today the identity the whole UI keys on is derived from the tmux pane command (`DetectAgentTool`), and it surfaces as a brand badge on every session row, a vendor segmented switch in the session bar, a "Harness wählen" menu on creation, a default-vendor preference, and a "Zu X wechseln" action. Under omp the vendor is the same for every Session and therefore distinguishes nothing, so the visible identity becomes the model and its provider — which also means it can change during a Session and the surfaces must follow. **BREAKING** for anyone used to picking a harness per Session.
- **Every surface that assumed a terminal, a vendor or one vendor's prices is rewritten.** The "Claude-Limits" usage pager and the TUI's "Claude-Usage" section, the statistics model grouping that parses `^claude-(opus|sonnet|haiku)`, the Claude-only pricing table, the search placeholder promising "alle Claude-Session-Transkripte", the Claude icon on the statistics navigation, the kill confirmation that names a tmux session, the TUI detail panel's captured pane preview, and the notch overlay that builds a permission prompt out of the last six scraped pane lines and tells the developer the question "ist im Terminal geöffnet". Each is replaced by what is actually true under omp rather than left to read wrongly.
- **The approval gate is enforced, proven, and fail-closed.** omp's own schema default is `tools.approvalMode: yolo`, which auto-approves reads, writes and execution. Magentic SHALL launch every omp Session with `--approval-mode always-ask`. omp does not report its own approval mode — verified against the installed build — so the gate cannot be confirmed by asking a running session; it is proven instead from launch provenance under confirmed process identity, and the mechanism itself is verified behaviorally against each omp build in a throwaway session before any real Session may start. A gate that cannot be proven refuses the Session with a stated reason. **No permission decision is ever made on the developer's behalf**, which is the property `replace-tmux-agent-runtime` already established and this change must not weaken while changing the mechanism under it.
- **One vendor, one run identity.** `AgentVendor` becomes `omp` for every coding-agent Session, qualified by omp's own `sessionId`. The model provider behind a turn (`anthropic`, `openai`, `ollama`, …) becomes a recorded fact carried alongside the Item, not a second identity. This keeps ADR 0001 intact: run identities stay vendor-qualified, and the vendor is now the thing that actually owns the record.
- **One normalizer.** omp's lifecycle and message events are normalized into the Items `agent-timeline` defines, in one normalizer, satisfying ADR 0005. Magentic MUST NOT read omp's session JSONL: the format is documented as internal and its bucket-naming scheme already changed between releases.
- **Status comes off the protocol, not off a screen.** `turn_start`, `turn_end`, `agent_end` (honouring `isTerminal !== false`) and a pending approval request give working, done and awaiting-decision as reported facts, and `StatusSource` gains a fourth member. These events come from omp's RPC reference rather than from the probe run for this proposal; design.md separates what was exercised from what was only read, and a spike confirms the difference before the work that depends on it starts. The unknown contract of ADR 0004 is unchanged: a status the protocol did not report stays unknown, and prompt delivery stays fail-closed on unknown.
- **The per-vendor launch and drive path is removed.** The four `AgentProvider` implementations collapse to one; the coding-agent pane manifests in `core/agents/*.yaml` and their evaluator lose their status role; `hookinstall.go` and the Claude status-line reporter go; `ClaudeManagedArgv` and the Claude-only managed runtime go; the per-vendor handoff storage hints and `SwitchVendor` go.
- **The per-vendor *read* path stays.** Retiring the ability to *launch* Claude Code must not retire the ability to *read* what it already wrote. The history adapters and the Claude conversation normalizer are kept for records already on disk, so statistics, past Conversations and resumable Sessions created before this change survive. They become read-only legacy readers rather than halves of a live integration.
- **Existing work is imported rather than abandoned.** omp ships `--from-claude` and `--from-codex`, which import an existing session into omp. Resuming a pre-omp Session offers that import as the path forward, and states plainly when a vendor has no importer.

### Non-goals

- Removing tmux. Terminal Sessions, the terminal dock and `T` are untouched; only coding agents leave tmux.
- Reimplementing omp's TUI. Magentic drives omp as a host and does not reproduce its interactive surface; a developer who wants omp's own interface gets a terminal into the same session.
- Deciding permissions automatically, in any mode, for any tool class. `--auto-approve` and `--approval-mode yolo` are not configurable from Magentic.
- Multi-machine or remote omp. `add-remote-client-access` owns that question.
- Reading or writing omp's session files, auth database, or configuration directly. Everything goes through the protocol or through documented flags.
- Surviving a reboot. Unchanged from `replace-tmux-agent-runtime`: the daemon reclaims its own processes, it does not rescue what an OS restart killed.

## Capabilities

### New Capabilities

- `omp-runtime/runtime-adoption`: omp as the runtime every coding-agent Session receives, what tmux retains, which Session actions exist under omp, and how an existing tmux or managed Session is carried across.
- `omp-runtime/process-ownership`: the daemon launching, owning, supervising, reclaiming and stopping omp processes; the launch argument list and profile; protocol handshake and version negotiation; and how an unusable omp is refused rather than worked around.
- `omp-runtime/approval-gate`: forcing an asking approval mode, proving it is active before the Session accepts work, routing a tool approval to a person, and the fail-closed behavior when the gate cannot be proven or an open request outlives its process.
- `omp-runtime/session-control`: the controls Magentic's interfaces offer over a live omp Session — model, thinking level, fast mode, compaction, steering, follow-up, interrupt — and the state they read back.
- `omp-runtime/status-and-lifecycle`: deriving Session status from protocol lifecycle events, the added status source, turn boundaries and delivery acknowledgement, and the unchanged unknown contract.
- `omp-runtime/conversation-normalization`: normalizing omp's event stream into Items and Conversations, the recorded model provider, and the prohibition on reading omp's session files.
- `omp-runtime/vendor-retirement`: what per-vendor launch and detection machinery is removed, what legacy read machinery is kept and under what contract, and how a pre-omp Session is imported or explicitly declared un-importable.
- `omp-runtime/interface-surfaces`: how the change is made visible in every surface of both interfaces — the model replacing the vendor as a Session's identity, the removal of vendor choices, the replacement of terminal-shaped affordances, approval prompts presented from the request rather than from a screen, provider-named usage and cost, the visible state of the approval gate, and refusals shown with their cause.

### Modified Capabilities

- `agent-timeline/item-model`: the requirement that every supported agent vendor declares whether it can be normalized is kept, but *vendor* is redefined. It becomes the agent that recorded the activity (omp, or a legacy vendor whose records predate this change), and the model provider that served the turn becomes a separate recorded fact an Item may carry. Without this, `vendor` means two things at once the moment one agent fronts sixty providers.
- `agent-timeline/conversation-reading`: incremental reading assumes a vendor file on disk that grows and can be re-read — it speaks of records appended since the previous reading, of a rewritten record forcing a full re-read, and of skipping a partially written trailing record. An omp Conversation is accumulated from a live stream instead, so those requirements are restated to hold for both a record at rest and a stream in flight, including an honest replacement for the rule that unwatched Sessions are not read.
- `agent-timeline/conversation-view`: the surface is required to offer the way to a waiting Session's terminal, and states that the terminal remains the only complete reading. A coding-agent Session under omp has no terminal of its own, so the route becomes omp's own interface — and because opening it withdraws Magentic's proof that the Session's tools are gated, the surface must not present it as consequence-free. The prohibition on offering approval controls in this surface is carried over unchanged.

## Impact

- **Depends on `replace-tmux-agent-runtime`.** The agent host, identity-confirmed reclaim, permission-request store, service installation and non-tmux observation path (`core/agenthost.go`, `core/agenthost_process.go`, `core/managed_protocol.go`, `core/managed_turn.go`, `core/observation_managed.go`, `core/control_managed.go`) are the scaffolding this change substitutes a protocol into. Its remaining 17 open tasks should be read as shared groundwork, not as competing work.
- **Supersedes a non-goal of `replace-tmux-agent-runtime`**: "Driving Codex, Gemini CLI or GitHub Copilot headless." That exclusion existed because each vendor needed its own headless integration. It stops being true when one runtime fronts all of them.
- **Narrows `add-vendor-agnostic-agent-status`** rather than discarding it. Its status vocabulary, `StatusSource`, `done`-versus-`idle` distinction and unknown contract are all reused. Its pane manifests keep owning *recognition* for terminal Sessions but stop being a coding-agent status source. Note the coupling: `AgentProvider.Matches` delegates to the manifests' pane-command patterns, so the manifests cannot simply be deleted.
- `core/provider.go`, `core/provider_catalog.go`, `core/provider_run.go`: four vendor adapters collapse to one; the vendor picker becomes a model picker.
- `core/lifecycle.go`, `core/lifecycle_tmux.go`: `Provision` defaults to the omp runtime, `SwitchVendor` is removed, and worktree provisioning is unchanged. ADR 0003 still governs — durable intent before any runtime is touched.
- `core/observation.go`, `core/status.go`, `core/agentkind.go`, `core/agentkind_eval.go`, `core/agents/*.yaml`: coding-agent status stops being inferred from `capture-pane`; the manifests keep their recognition role for terminal Sessions.
- `core/outbox.go`, `core/actions.go`: `sendPromptLiteralValidated`'s `send-keys` path and its bracketed-paste wrapper stop applying to coding agents; delivery becomes acknowledged.
- `core/timeline.go`, `core/timeline_claude.go`, `core/claude_record.go`: the normalizer registry gains omp; Claude's normalizer is retained as a legacy reader for existing records.
- `core/workhistory_adapters.go`, `core/usage_*.go`, `core/stats.go`, `core/overview.go`: history and pricing gain omp; the five existing adapters become legacy readers. Pricing across sixty providers is an open question this change must answer rather than inherit.
- `core/handoff.go`: per-vendor storage-path hints lose their purpose once one agent owns the record, and the vendor-switch handoff goes with `SwitchVendor`.
- `core/control.go`, `core/control_dispatch.go`, `core/control_managed.go`: `session.start` stops taking a vendor and starts taking a model; new verbs cover the session controls.
- `core/state.go`: `AgentRuntime` gains `omp`; absence must keep reading as tmux so existing records survive without a migration pass.
- `app/frontend/src/` (plain ES modules, no framework, ~40 files): `avatar.js`'s per-vendor brand icons and label table become model-provider identity; `session-tool.js`'s identity resolution loses its pane-command basis; `main.js` loses `showVendorMenu`, `vendorSwitchHtml`, the default-vendor preference and the "Zu X wechseln" menu row, and gains the model and thinking-level controls; `stats.js`'s `modelLabel` stops parsing Claude model names; `usage-state.js` and the usage pager stop being Claude-shaped; `conversation.js` and `conversation-state.js` lose the "Zum Terminal dieser Session" notices; `dock.js`'s surface switch and `hydra-handoff.js`'s cross-vendor handoff change or go; `preview-sample.js`'s canned Claude Code splash and `index.html`'s search placeholder are rewritten.
- `app/notch.go` and `NotchOverlay.js`: the permission overlay's detail comes from the approval request instead of `core/attention.go`'s six-line pane excerpt, and the question kind stops pointing at a terminal.
- `view.go`, `model.go`: the TUI's "neue Claude-Session", its "Claude-Usage" section, the captured-pane preview in the detail panel, the `⏎ attach` action for coding-agent Sessions, and the kill confirmation naming tmux.
- `core/status.go`: `DetectAgentTool` derives the tool identity the whole UI keys on from the tmux pane command, which no omp Session has.
- `core/overview.go`, `core/usage.go`, `core/stats.go`: "Claude-Limits" and the Claude-only pricing table become provider-named and explicitly incomplete where unknown.
- `core/resume.go`: the resumability reasons naming a managed runtime and an unknown vendor.
- `CONTEXT.md`, `PRODUCT.md`, `README.md`, `docs/adr/`: *vendor* is redefined, README's tmux promise narrows to terminal Sessions, PRODUCT.md's operating context changes, and making one third-party binary the sole agent runtime deserves its own ADR.
- **New external dependency.** Magentic gains a hard runtime dependency on a third-party binary that ships roughly daily and publishes no compatibility policy for its RPC command and event vocabulary. The `ready` frame versions the framing, not the schema. This is the central risk of the change and design.md must carry it rather than the proposal glossing it.
